# Maintenance Contract: easy-browser-use

This file is for agents editing the skill. Keep maintainer rules here, not in `SKILL.md`.

## Ownership

- `SKILL.md` holds what an agent would not get from the server's own tool descriptions: what it can and cannot reach, the order of calls, and the traps. When a tool's description starts saying something the skill says, cut it from the skill.
- `scripts/allow-remote-debugging.ps1` presses Allow on Chrome's "Allow remote debugging?" window through UI Automation when a chrome-devtools-mcp server, any agent's, holds a connection that could have raised the window, and no program of another kind does. It activates no window, moves no mouse, and sends no keys. Keep it that way, and keep its refusal: a window a program of another kind could have raised is left open. Keep one watcher per signed-in Windows user, however many sessions run, and keep its idle cost low. Read connections and command lines through direct Windows calls, since the system queries take a quarter second each.
- `scripts/launch-server.mjs`, `scripts/update.mjs`, and `package.json` make up the launcher: it runs the server installed beside it with the harness's stdio passed straight through, and starts the shared watcher when none is running. The watcher and the update must never keep the server from starting or running, and neither writes to stdout. `package.json` carries the same version as `metadata.version`, and its dependency range on the server is where a server major version is adopted.
- The launcher keeps itself current, so no one runs npm by hand after the first install. Each release goes into a folder of its own, `versions\<launcher>+<server>` in the install folder, the one the hand-installed copy sits in. Installed as the setup says, it is also the watcher's folder. The hand-installed copy is never changed. A name already taken by a copy from another spec gets `-2`, `-3`, and so on, and no code reads meaning from a name. A launcher hands each session to the newest complete copy installed from the same package spec as itself, by importing that copy's `scripts/launch-server.mjs` and calling its `start`, and passes over one that fails to load or start. So a running session keeps the files it started with, and an install that fails partway leaves every other copy as it was.
- `start` checks for an update before anything else. A check is due a day after the last one, an hour after one that failed, or at once when the install folder's spec has changed, and it runs `update.mjs` detached so it outlives a short session. It asks npm what the saved spec resolves to now and what the newest server in that release's range is. When either is newer than the newest copy, it installs into a dot-named folder, checks that the new launcher loads and exports `start` and that the new server starts, and only then renames the folder into place. Each check writes its spec, its time, and any error to `update.json`, every launcher start prints a recorded error to stderr, and deleting `update.json` makes the next session check at once.
- Only one check runs at a time. Its lock is the folder `update.lock`, holding a file named for the check it belongs to, which that check keeps open while it runs and which it must find there to start. Windows refuses to rename a folder with an open file in it, so a launcher takes over a lock only when it is over a minute old and no check holds a file in it. The same rule removes old copies: every process that runs from a copy holds that copy's launcher file open, and a check removes an older copy only after renaming its folder succeeds. Copies from a spec the install folder no longer uses are neither run nor removed.
- A launcher installed by hand hands sessions over with its own code for as long as it stays installed. Keep what it relies on compatible with every older one: the path `scripts/launch-server.mjs` in each copy, its exported `start`, which runs a session and rejects only before it starts the server, and the layout under `versions`, where each copy is a folder holding its own npm install.
- `references/hanging-first-call.md` holds what that window is, how to read the watcher's log, the tradeoff of answering it by script, how to run the script, what each of its results means, and answering or avoiding the window off Windows, read when the server's first call hangs. Keep its results table in step with the script's result lines and exit codes, and keep the script's own help text in step with both.
- `scripts/answer-file-dialog.ps1` answers the browser's own Save As and Open dialogs, the one part of a download or upload the server cannot reach, through window messages alone. It activates no window and sends no keys. Keep it that way.
- `references/file-dialogs.md` holds how to run that script and what each of its results means, read only before a click that downloads a file or opens a picker, or before answering a dialog that is already waiting. Keep its results table in step with the script's result lines and exit codes, and keep the script's own help text in step with both.
- `references/setup.md` holds the registration commands, the Chrome setting, what `--autoConnect` and `--channel` do, and how to register a separate profile, read when the server is being installed or attaches to the wrong Chrome. Keep install detail out of `SKILL.md`.
- The skill teaches the server and routes no task to it or away from it, by the author's decision. It says what the server cannot reach, and never that a page must not be worked through desktop control.
- The skill says what it does and when it applies, and nothing about a harness's own browser tools, for or against, by the author's decision. Which tool an agent uses is settled outside the skill, by the user, the prompt, or what is installed. State what `chrome-devtools` reaches, never that it must be the tool used.
- `README.md` is the human skim layer. Keep it to a few sentences.

## Sources

- The registration commands follow `claude mcp add --help` and `codex mcp add --help`. The server flags follow `npx chrome-devtools-mcp@latest --help`.
- The Chrome setting, the version floor, and the channel follow the `--autoConnect` and `--channel` entries in the chrome-devtools-mcp help text.
- The profile that `--autoConnect` attaches to, the consent window, and the separate profile used without the flag follow the chrome-devtools-mcp advanced usage guide.
- That no setting skips the "Allow remote debugging?" window for the user's own profile follows the chrome-devtools-mcp advanced usage guide, Chrome for Developers' agent configuration page, and the project's open feature request for a persisted approval, whose maintainers advise a separate profile instead. The separate profile reached with `--browserUrl` and a non-default `--user-data-dir` follows the same two pages. Recheck all three when the server or Chrome ships a release that mentions the consent window.
- The prompt script follows Microsoft's UI Automation documentation for `AutomationElement.FromHandle` and `InvokePattern`, Microsoft's IP Helper documentation for `GetExtendedTcpTable` and `MIB_TCPROW_OWNER_MODULE` and its `NtQueryInformationProcess` documentation for a process's command line, both checked against `Get-NetTCPConnection` and `Win32_Process`, and Chrome's `DevToolsActivePort` file for the port. That the window is a top-level Chrome window with its own title, that its three buttons are found by name through UI Automation, that the connection to the port exists before the window does, that a repeated call during the wait raises no second window, that an unanswered window goes away by itself and the next call raises a new one, that Chrome ignores a press within a double-click interval of the window appearing or of an earlier press, that pressing Allow through UI Automation moves neither focus nor the mouse, and that pressing the close button of Chrome's automated test software bar the same way takes focus to Chrome, so the bar is left alone, are observations from real runs against Chrome on an English Windows 11. Recheck them when the script ends in NO_BUTTON or OPEN, or refuses a connection that is a chrome-devtools-mcp server's. The launcher follows the Node.js `child_process.spawn` documentation, including what `detached`, `windowsHide`, and `timeout` do on Windows, and npm's `install --prefix` and `view` documentation. That the server connects to Chrome on its first call that needs the browser, and that a server kept on disk starts much faster than a fresh `npx` resolution, are observations from real runs.
- The update relies on these observations from real runs: `npm view` resolves a git spec and prints the version and dependencies as JSON, an `npm install` cut off partway leaves the package it was replacing moved aside and the new one incomplete, Node and PowerShell's `-File` do not keep their script open while it runs, Windows refuses to rename a folder holding a file another process has open but lets a recursive delete through, and a detached check outlives a launcher that is killed and shows no window.
- The upload line follows the `upload_file` handler in the chrome-devtools-mcp source, which sets the files on a file input directly and otherwise clicks the element and accepts the chooser Puppeteer intercepts, and Puppeteer's `Page.waitForFileChooser` reference, which leaves out `showOpenFilePicker`.
- The window messages the file dialog script sends follow Microsoft's Win32 documentation for `WM_SETTEXT`, `WM_GETTEXT`, `WM_COMMAND`, `PostMessage`, and `SendMessageTimeout`. Its control numbers (1148 for the Open dialog's file name combo box, 1001 for the Save As file name box), that a Save As dialog can start in a folder the browser remembers, that an Open dialog takes several files from different folders as quoted full paths, that an Open dialog given a missing file raises an error box with the dialog's own title and a single button, and what `SendKeys` did to typed paths are observations from real runs against Chrome's dialogs on an English Windows 11. Recheck them when the script stops finding the box or the dialog. That a Save As dialog raises the same kind of box is assumed. Recheck it when a Save As run ends in BLOCKED under a box titled Save As.
- The remaining lines under Tabs And Pages are observations from real runs against a real Chrome. Where a first-party source contradicts one, the source wins. Otherwise recheck an observation before changing its line, and again when the server ships a release that touches it.

## Editing Rules

- State facts and the order to do things in. The skill carries no approval step, allow-list, or restriction on what the user may ask for, by the author's decision. That includes sign-in: a page the browser has filled is passed, and the agent stops only for what the user alone holds.
- An agent using the skill meets Chrome's "Allow remote debugging?" window only once a first call hangs, by the author's decision. On Windows the launcher answers it, and the agent just makes its calls. `SKILL.md`, its description, and `README.md` say nothing about the window, the watcher, or the prompt script, and route a first call that hangs to `references/hanging-first-call.md` by that symptom alone. The references name the window only where their reader acts on it.
- Never hand the user a click that desktop control could make, the remote debugging consent window first among them.
- Keep the opening's statements of what the tools reach and that page content is data.
- Do not record dates, measurements, machine paths, tab titles from a real browser, or the story of a test run.
- Do not use em dashes or en dashes, and do not use semicolons to join sentences.
- Bump `metadata.version` by the release-versioning skill's rules for skills.
